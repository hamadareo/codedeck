# Phase 3 実装計画(使用量と通知)

利用者の指示(2026-10-10「まだチームプランの追加はできませんができるところから進めてください」)を承認として扱う。

## 範囲(§7、§5 の「通知」)
1. **集計**: プロファイルの `projects/` 配下の会話の記録(JSONL)から、assistant の行の `message.usage` と `timestamp` だけを読み、5時間ウィンドウと7日ウィンドウの消費を推定する。本文やプロンプトは読まず、保存もしない
2. **上限値**: プロファイルごとに設定できる。`claude auth status` の `subscriptionType`(pro / max / team など)から仮の目安を出し、利用者が上書きできる。上限に達したメッセージを検出したら、その時点の消費量を「実測の上限」として記録し、目安より優先する(手で設定した値は上書きしない)
3. **実測との併用**: ターミナル出力の「上限に達した」旨のメッセージを検出し、セッションの状態を「上限到達」にして、リセット時刻を表示する(出力は読むだけで、書き換えない)
4. **しきい値通知**: 既定 70% / 90% / 100%、プロファイル別に変更可。同じウィンドウの同じしきい値は1回だけ(再起動しても重複しない)
5. **通知先**: OS 標準通知(macOS 通知センター / Windows トースト)、アプリ内バナー。種類ごとに ON/OFF。Discord は Phase 4
6. **リセット通知**: 90% 以上になった、または上限に達した5時間ウィンドウが終わったら「再び使えます」(任意、既定 ON)
7. **表示**: サイドバーのプロファイルごとに使用量バー(5時間 / 7日)とリセットまでの時間。トレイ(メニューバー)にも同じ内容
8. **セッションの通知**(§5): 完了 / 承認待ち / エラー を、アプリが前面にないときに OS 通知で知らせる。クリックでそのセッションを表示

## 推定の方法
- トークン数 = `input_tokens + output_tokens + cache_creation_input_tokens`(キャッシュの読み込みは含めない)。同じ `message.id` + `requestId` は1回だけ数える
- 5時間ウィンドウ: 最初のメッセージの時刻(時の単位に切り捨て)から5時間。その後の最初のメッセージで次のウィンドウが始まる
- 7日ウィンドウ: 直近7日間の合計(移動窓)。「リセット」は、いちばん古い記録が窓から外れる時刻
- 公式の上限値は公開されていないため、目安は**非公式の仮の値**であることを画面に明記する。非公開の API は使わない

## データ
- SQLite v3: `profile_usage(profile_id PK, plan, limit_5h, limit_7d, limit_source, thresholds)`、`usage_alerts(profile_id, window, window_key, threshold, created_at)`(通知の重複防止)
- settings.json: `notifications`(OS / アプリ内 / 種類ごとの ON/OFF)

## テスト
- ユニット: JSONL の読み取り(追記分だけ読む、重複の除外、壊れた行、本文を保持しないこと)、ウィンドウの計算、しきい値の判定(飛び越し、重複なし、再起動後も重複なし)、リセット通知、上限メッセージの検出
- E2E: テスト用の会話の記録をプロファイルに置き、しきい値を超えたら通知が1回だけ出ること(アプリ内バナーと通知の履歴)、サイドバーのバー表示
